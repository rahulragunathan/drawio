# Known Issues

Open defects, most severe first. [ROADMAP.md](ROADMAP.md) carries the one-line index; this
file carries enough detail to pick an item up without digging.

Each entry has a stable ID — use it in branch names (`bugfix/ki-02-<slug>`) and in the
CHANGELOG entry that closes it. When fixed, delete it from here and from the ROADMAP index;
the record lives in [CHANGELOG.md](../CHANGELOG.md). IDs are never reused.

## Severity

| Level | Means |
| ------- | ------- |
| **Critical** | Loses or corrupts data, or sends wrong information to real recipients. |
| **High** | Silently produces a wrong result, or reports success without doing the work. |
| **Medium** | Wrong under conditions the operator can notice or work around. |
| **Low** | Cosmetic, or wrong in a field nothing consumes. |

## KI-02 — A compressed .drawio validates as clean no matter what it contains

**Severity:** High
**Where:** [scripts/validate.py:354](../scripts/validate.py#L354), `parse_drawio`

### What happens

`parse_drawio` parses the file as plain XML and walks `mxCell` elements:

```python
tree = ET.parse(path)
root = tree.getroot()
...
for cell in root.findall(".//mxCell"):
```

draw.io also writes a **compressed** form, where `<diagram>` holds a single
base64 string of deflate-compressed, URL-encoded XML and there are no `mxCell`
descendants at all. Nothing decodes it and nothing notices it is missing, so
`boxes` and `edges` come back empty, every check iterates over nothing, and the
CLI prints `✓ no violations` and exits 0.

The failure is silent and inverted: the emptier the parse, the cleaner the
result looks.

### Example scenario

Reproduced against the repo at 1.4.0, using the suite's own `build_crossing`
fixture:

```text
UNCOMPRESSED -> exit 1 | ✗ CROSSING: edge '' (A → C) segment (180.0, 225.0)→(500.0, 225.0) …
COMPRESSED   -> exit 0 | ✓ no violations
```

Same diagram, same violation, opposite verdict. Any diagram a user saved from
draw.io with compression on — the browser app's default for some save paths —
passes review without being looked at.

### Notes for a fix

Detect and decode before parsing: when a `<diagram>` element has no `mxCell`
child but non-empty text, treat the text as base64 → `zlib.decompress(data,
-15)` → `urllib.parse.unquote` → parse that as XML. All three steps are stdlib,
so the constraint in [CLAUDE.md](../CLAUDE.md) holds.

Decide deliberately whether an undecodable `<diagram>` is an error or a warning.
Failing loudly is the safer default here — the whole defect is that "nothing
found" currently reads as "nothing wrong". A file with zero parsed cells should
never report clean; that guard is worth adding on its own, independently of
compression support, because it also catches a malformed file.

Bundle with [KI-03](#ki-03): both are defects in how the file is read rather
than in any check, and both want the same new fixture family.

**Source:** gpt-5.6-sol — repo review, 1.4.0

## KI-03 — Multi-page diagrams are merged into one canvas by non-unique cell IDs

**Severity:** High
**Where:** [scripts/validate.py:362](../scripts/validate.py#L362), `parse_drawio`

### What happens

The parser searches from the document root:

```python
edge_ids = {c.get("id") for c in root.findall(".//mxCell") if c.get("edge") == "1"}
```

`.//mxCell` descends into **every** `<diagram>` page, and the results go into a
single `boxes` dict keyed by cell ID. Cell IDs are unique per page, not per
file, and draw.io hands out `2`, `3`, `4`… on each new page. Page two's box `2`
therefore overwrites page one's box `2`.

The consequences run in both directions. An edge on page one can resolve its
source to a shape on page two and be checked against coordinates it never
touches; two shapes that overlap only because they live on different pages are
reported as colliding; and a genuine violation on an overwritten shape
disappears.

### Example scenario

A user keeps a system diagram on page 1 and a sequence detail on page 2, both
generated by draw.io with default IDs. Page 2 has a box at (100, 100); page 1
has an unrelated box with the same ID at (900, 600). Validation reports a
`CROSSING` on page 1 against a rectangle that only exists on page 2, and the
user cannot find the box the message names.

### Notes for a fix

Parse per `<diagram>` element and validate each page independently, reporting
violations with the page name. `validate()` currently returns a flat list of
strings, and `main()` prints them under one filename heading, so the page label
has to be carried into the message text or the return type has to change —
`scripts/render_examples.py` and `scripts/preview.py` both consume
`validate()`/`parse_drawio`, so check those call sites before changing a
signature.

The narrower alternative is to namespace IDs by page index during the parse.
That fixes collisions without restructuring, but leaves cross-page geometry
being compared as if it were one canvas, so it is a half-fix.

Bundle with [KI-02](#ki-02).

**Source:** gpt-5.6-sol — repo review, 1.4.0

## KI-04 — Stub squaring accepts a stub that leaves the anchor in the wrong direction

**Severity:** High
**Where:** [scripts/validate.py:495-516](../scripts/validate.py#L495-L516), `_square_front` / `_square_back`

### What happens

Both helpers bail out as soon as the first segment is axis-aligned:

```python
a, nxt = pts[0], pts[1]
if segment_is_orthogonal(a, nxt):
    return pts
```

`segment_is_orthogonal` answers "horizontal **or** vertical". The `horizontal`
argument — which side of the box the anchor sits on, and therefore which way
draw.io's `orthogonalEdgeStyle` must leave — is computed and then ignored on
this path.

So an edge exiting a right-side anchor (`exitX=1`) whose first waypoint sits
directly *below* the anchor is accepted as a vertical stub. draw.io renders it
as a jetty out to the right, then down, then back in. The validator checks a
route that is not drawn: crossings along the real horizontal stub are missed,
and the reconstructed vertical line often hugs or clips the source box.

This is the same class of bug that stub squaring exists to prevent, in the one
case the early return skips. `tests/test_validate.py`'s stub guard covers only a
diagonal stub, which is the branch that does work.

### Example scenario

`edge(src, dst, exitX=1, exitY=0.5, waypoints=[(x_of_anchor, 600)])` with a box
sitting to the right of the source at y≈300. draw.io draws the arrow out to the
right and straight through that box; the validator models a clean vertical drop
and reports no `CROSSING`.

### Notes for a fix

Replace the orthogonality test with a direction test: the front stub is already
correct only when it travels along the required axis — horizontal when
`horizontal` is `True`, vertical when it is `False`. Otherwise insert the corner.
`_square_back` needs the mirrored change.

Watch the `None` case: `_anchor_travels_horizontally` returns `None` for an
unanchored or interior-anchored endpoint, and both helpers must keep returning
`pts` untouched there — that is not a wrong direction, it is an unknown one.

Guard with a fixture per side (right-edge anchor with a vertically aligned
waypoint, bottom-edge anchor with a horizontally aligned one) that must fire,
plus the existing diagonal-stub guard that must not.

**Both reviewers found this independently.**

**Source:** gpt-5.6-sol, gemini-3.1-pro-high — repo review, 1.4.0

## KI-05 — A label in a separate edgeLabel cell escapes every label check

**Severity:** High
**Where:** [scripts/validate.py:389](../scripts/validate.py#L389) and [:466](../scripts/validate.py#L466), `parse_drawio`

### What happens

An edge's label text is read only from the edge cell itself:

```python
Edge(cid, cell.get("source"), ..., cell.get("value") or "", ...)
```

But draw.io Desktop moves a label onto its own child vertex on round-trip, and
the parser drops that vertex entirely:

```python
if geom.get("relative") == "1" or parent_id in edge_ids:
    continue
```

Skipping it as an *obstacle* is right — its geometry is a fraction along the
edge, not a rectangle. Skipping its *text* is not. The parent edge keeps
`label == ""`, so `LABEL_OVERLAP`, `LABEL_BOX_OVERLAP` and
`SHORT_LABELLED_EDGE` all treat the edge as unlabelled and never run, while the
label is plainly visible in draw.io.

[SKILL.md](../SKILL.md) documents separate `edgeLabel` children as a normal
Desktop round-trip artifact, so this is the expected shape of any hand-tuned
file — exactly the files most likely to have label problems.

### Example scenario

Generate a diagram, open it in Desktop, drag one edge label to a better spot,
save. The label now lives in a child cell. Re-run the validator: it reports no
label violations at all for that edge, including a label parked squarely on top
of another one.

### Notes for a fix

While skipping the child, hoist its `value` onto the parent edge, and take its
`mxGeometry` `x` (position along the path) and `offset` point as the label
position — which is also what [KI-08](#ki-08) needs. Handle more than one child
label per edge by taking the first non-empty one.

Bundle with [KI-06](#ki-06) and [KI-08](#ki-08): all three are about reading a
label's text and position out of the shapes draw.io actually writes.

**Source:** gpt-5.6-sol — repo review, 1.4.0

## KI-01 — The icon catalog publishes keys the generator helpers reject

**Severity:** Medium
**Where:** [references/icons.md](../references/icons.md) · [scripts/list_icons.py:253-256](../scripts/list_icons.py#L253-L256) · [assets/build_template.py:404-405](../assets/build_template.py#L404-L405)

### What happens

There are two icon key formats and the workflow crosses them.

The catalog and its tooling use a **hyphen**. `load_catalog()` splits the family off the
front of the key:

```python
key = m.group("key")
family = key.split("-", 1)[0]
```

so `--search lambda` prints `aws-lambda`, and `references/icons.md` opens with

```python
icon_box(40, 80, 220, 60, "Order Handler", fill=..., icon="aws-lambda")
```

The helpers use a **colon**. `icon_style()` in `assets/build_template.py` and in both
examples does:

```python
family, _, name = str(icon).partition(":")
kind, prefix, wrapper, glyph_key, bare = ICON_FAMILIES[family]
```

`"aws-lambda".partition(":")` yields the family `aws-lambda`, which is not a key of
`ICON_FAMILIES`, so the lookup raises. The two forms are related by replacing the first
hyphen with a colon, and nothing says so.

SKILL.md compounds it. Under "Choosing an icon" it states that names live in
`references/icons.md` as `family:name`. They do not — the catalog lists `aws-lambda` with
the draw.io name `lambda` in a separate column.

### Example scenario

Follow the documented workflow exactly:

```bash
python scripts/list_icons.py --search lambda      # prints: aws-lambda   lambda
```

Paste that key into a generator copied from the template:

```python
icon_box(620, 160, 220, 64, "<b>Handler</b>", fill=COMPUTE, icon="aws-lambda")
```

Running it raises `KeyError: 'aws-lambda'` before any XML is written. The user has to guess
that `aws:lambda` is meant. Verified against `assets/build_template.py` at the current
commit; `aws:lambda` returns
`shape=mxgraph.aws4.resourceIcon;resIcon=mxgraph.aws4.lambda;` as intended.

### Notes for a fix

Pick one format and make everything speak it. The colon form is the one the helpers, both
examples and SKILL.md already use, and it is the form that ends up in a diagram — so the
cheaper move is to change what the catalog side *emits*, not what the helpers accept:

- `--search` should print the string a user pastes (`aws:lambda`), not the internal row key.
- `references/icons.md`'s opening snippet must use the same string as its tables.
- `load_catalog()` keys the catalog dict on the row key, and `qualified_names()` and the
  `--verify` path both read `entry["family"]`. Changing the row key format touches
  `tests/test_list_icons.py`, which asserts parsed keys directly.

Accepting the hyphen form in `icon_style()` as well is a one-line alternative
(`partition(":")` then `partition("-")`), but it leaves two spellings in circulation and
does not fix the SKILL.md claim.

**The regression net is the gap that let this through:** no test builds a diagram from a key
the catalog actually publishes. Add one that reads a key out of `load_catalog()`, feeds it to
the template's `icon_style()`, and asserts a valid stencil name comes back. That test fails
today and would have caught this on the commit that introduced the catalog.

**Source:** found during the 1.4.0 documentation drift check.

## KI-06 — Labels on `<object>` wrappers are lost

**Severity:** Medium
**Where:** [scripts/validate.py:408](../scripts/validate.py#L408) and [:466](../scripts/validate.py#L466), `parse_drawio`

### What happens

The parser reaches cells with `root.findall(".//mxCell")` and reads text with
`cell.get("value")`. When draw.io attaches metadata to a cell it wraps it:

```xml
<object label="Publish Events" tooltip="…" id="7">
  <mxCell style="…" edge="1" parent="1" source="3" target="5">…</mxCell>
</object>
```

The visible text is now the wrapper's `label` attribute, and the inner `mxCell`
has no `value`. `.//mxCell` still finds the cell, so the shape or edge is
checked geometrically, but its label is empty — the same blind spot as
[KI-05](#ki-05), reached by a different route. Violation messages for these
cells also print blank names, which makes them hard to act on.

Note the ID moves too: on a wrapped cell the `id` lives on the `<object>`, so an
edge referencing it by `source`/`target` may not resolve.

### Example scenario

Add a link or a tooltip to an edge in draw.io — a common thing to do on a
diagram meant for sharing — and that edge's label silently stops being measured.

### Notes for a fix

Iterate over `<object>` elements as well, or walk the tree once and, for each
`mxCell`, look at its parent element for `label` and `id`. Prefer the wrapper's
`label` when the cell's own `value` is empty. Add a fixture with a wrapped edge
and a wrapped box.

**Source:** gpt-5.6-sol — repo review, 1.4.0

## KI-07 — The title-band exemption applies to every vertical segment of the edge

**Severity:** Medium
**Where:** [scripts/validate.py:987](../scripts/validate.py#L987), `validate`

### What happens

```python
if segment_is_vertical(a, b) and edge_endpoint_inside(edge, boxes, box):
    continue
```

`edge_endpoint_inside` asks a question about the **edge**, not about the
segment being tested. Once either endpoint sits anywhere inside a container,
*every* vertical segment of that edge is exempted from `TEXT_OVERLAP` against
that container — not just the entry stub that reaches the endpoint.

The documented intent, in [CLAUDE.md](../CLAUDE.md), is narrower: "the exemption
needs a *vertical* segment and an endpoint geometrically inside the container."
The horizontal half is genuinely narrow and `build_text_overlap_inside` guards
it. The vertical half is wider than it reads.

### Example scenario

A wide zone holds a service at its left edge. An edge starts at that service,
runs left out of the zone, up, right along the top, and then drops vertically
through the zone's title text on its way to a box further right inside the same
zone. That second vertical segment strikes through the title, and it is
exempted because the edge's source is inside the zone.

### Notes for a fix

Test proximity, not membership: exempt a vertical segment only when it is the
segment that actually reaches an inside endpoint — the first or last segment of
the polyline whose far end is that endpoint. `edge_endpoint_inside` already
resolves the endpoints, so the extra condition is which segment index is being
tested.

Add a fixture with two vertical segments against the same container, one an
entry stub and one a fly-over, and assert exactly one violation.

**Source:** gpt-5.6-sol — repo review, 1.4.0

## KI-08 — A label's position ignores the path-relative geometry draw.io stores

**Severity:** Medium
**Where:** [scripts/validate.py:553](../scripts/validate.py#L553), `edge_label_center`; [:448-451](../scripts/validate.py#L448-L451), `parse_drawio`

### What happens

`edge_label_center` places a label at the midpoint of the polyline's longest
segment, plus the `offset` point:

```python
"""draw.io places labels at the polyline's geometric center (midpoint of
its longest segment, roughly). We approximate by ..."""
```

draw.io actually positions a label at a *fraction along the whole path*, stored
as `x` on the label's `mxGeometry` (−1 to 1), with `offset` as a further nudge.
The parser reads only the `offset` mxPoint and never that `x`.

On a single-segment edge the two agree. On an L- or Z-shaped route they diverge,
and all three label checks then measure a rectangle that is not where the label
is — missing real overlaps and inventing ones that are not there.

The docstring is honest that this is an approximation. The problem is that the
docs do not carry that caveat, and the checks are trusted as exact.

### Example scenario

A three-segment route whose long horizontal run is at the far end from the
label. The user moved the label onto the short first hop in Desktop (setting
`x=-0.8`); the validator still measures it over the long run, and misses that it
now sits on top of a neighbouring box.

### Notes for a fix

Parse `mxGeometry`'s `x` for the edge and for any child label cell (see
[KI-05](#ki-05)), then walk the polyline by cumulative length to convert the
fraction into a point. Fall back to the current longest-segment midpoint when no
relative position is stored, which is what the skill's own generators produce —
so the bundled examples must keep validating unchanged.

Bundle with [KI-05](#ki-05) and [KI-06](#ki-06).

**Source:** gpt-5.6-sol — repo review, 1.4.0

## KI-09 — Icon name matching is case-insensitive for image paths, which are not

**Severity:** Low
**Where:** [scripts/validate.py:915](../scripts/validate.py#L915), `validate`

### What happens

```python
if ref in icon_universe or ref.lower() in lowered:
    continue
```

The case-insensitive fallback is applied to every reference. For a **stencil**
name that is reasonable — draw.io resolves those case-insensitively. For an
**image path** like `img/lib/azure2/compute/Function_Apps.svg` it is wrong: that
is a file path, resolved by a filesystem or a web server that may well be
case-sensitive.

So `UNKNOWN_ICON` accepts `function_apps.svg` because `Function_Apps.svg`
exists, and the icon renders as a blank plate on a case-sensitive host.

### Example scenario

An Azure icon typed with the wrong capitalisation validates clean, renders
correctly on macOS, and renders blank when the same file is opened from a
case-sensitive Linux checkout or served by a case-sensitive host.

### Notes for a fix

`icon_references()` already returns a `kind` alongside each reference. Apply the
lowercase fallback only for stencil kinds and require an exact match for image
paths, with a did-you-mean that names the correctly-cased file. Add one fixture
per kind.

**Source:** gpt-5.6-sol — repo review, 1.4.0

## KI-10 — Only four exact HTML break spellings are treated as line breaks

**Severity:** Low
**Where:** [scripts/validate.py:600](../scripts/validate.py#L600), `normalise_label`

### What happens

```python
s = label.replace("</div>", "\n").replace("<div>", "\n")
s = s.replace("<br/>", "\n").replace("<br>", "\n")
```

Four literal spellings. `<DIV>`, `<div style="...">`, `<br />` and any other
valid variant fall through to the generic tag stripper below, which deletes them
without breaking the line. A visibly two-line label is then measured as one line
of double the width.

This matters more than it looks, because it inverts the fix that
`normalise_label` exists for: measuring a stacked label as one long line is
exactly what produced false `SHORT_LABELLED_EDGE` warnings before 1.2.0. A
Desktop round-trip can rewrite a bare `<div>` as `<div style="…">`, so a file
that measured correctly when generated can start measuring wrong after an edit.

### Example scenario

`Verify<div style="text-align:center">Token</div>` measures as 11 characters on
one line (~61 px) instead of two lines of ≤6 (~33 px). On a 40 px edge that is a
`SHORT_LABELLED_EDGE` warning for a label that fits.

### Notes for a fix

Replace the literal `str.replace` chain with one case-insensitive regex for
opening and closing `div` and `br` tags with optional attributes and optional
self-closing slash — roughly `</?(?:div|br)\b[^>]*>`. The generic tag stripper
below it stays as the catch-all for everything else.

The parameterised cases in `tests/test_validate.py` cover the four exact
spellings today; extend them with the attribute and uppercase variants.

**Source:** gpt-5.6-sol — repo review, 1.4.0
